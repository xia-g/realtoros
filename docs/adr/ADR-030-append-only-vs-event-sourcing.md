# ADR-030: Append-only Event Log vs Full Event Sourcing

---

## Контекст

Stream 3 (Business Events) вводит единую событийную модель для Compliance Platform. 
Архитектурный вопрос: должна ли эта модель быть **полноценным Event Sourcing** 
(единственный источник истины — события, агрегаты восстанавливаются исключительно 
из событий) или **append-only журналом** (события — один из источников, текущее 
состояние хранится отдельно)?

Решение затрагивает:

- **Epic 3 требования к аудиту** — полная и неизменяемая запись всех изменений
- **Replay** — возможность восстановить состояние Consumer'а из истории событий
- **Интеграция между Streams** — Event Backbone как единый контракт
- **Все downstream Streams (4–11)** — их архитектура строится на этом решении

Существующий ADR-001 (Business Events как append-only журнал) описывает 
append-only **хранение**, но не отвечает на вопрос, должны ли события быть 
**единственным источником истины** для агрегатов.

---

## Рассмотренные альтернативы

### 1. Full Event Sourcing (не выбрано)

При full event sourcing всё состояние агрегата восстанавливается исключительно 
из событий. Текущее состояние — это projection, который всегда можно 
перестроить из event store.

```python
# Full event sourcing: агрегат не хранит текущее состояние
class ComplianceAggregate:
    """Агрегат, восстанавливаемый ТОЛЬКО из событий."""
    
    @classmethod
    async def load(cls, event_store, aggregate_id):
        events = await event_store.load_stream(aggregate_id)
        aggregate = cls()
        for event in events:
            aggregate.apply(event)
        return aggregate
    
    def apply(self, event):
        # Каждый event мутирует внутреннее состояние
        ...
```

**Плюсы:**
- Полная воспроизводимость — любое состояние можно восстановить из событий
- Нет расхождений между событиями и состоянием (single source of truth)
- Snapshot-based recovery для быстрого старта

**Минусы:**
- **Сложность домена** — Compliance имеет множество независимых агрегатов (State, 
  Eligibility, Dependency, Timeline), каждый со своей логикой восстановления
- **Сложность изменений** — изменение структуры агрегата требует миграции 
  всех событий или всех projection'ов
- **Производительность** — восстановление сложных агрегатов из длинной истории 
  событий может быть затратным (сотни событий на организацию × тысячи организаций)
- **Не все состояния представимы через события** — некоторые факты (например, 
  результат расчёта НДС) естественнее хранить как текущее состояние, а не 
  выводить из цепочки событий
- **Overengineering** — Compliance Layer не требует full event sourcing; 
  достаточно audit-совместимого журнала

### 2. Append-only Event Log + Current State (ВЫБРАН)

События записываются в неизменяемый журнал, но **текущее состояние хранится 
отдельно** (в проекциях/таблицах). События — не единственный источник истины.

```python
# Выбранная модель: события + отдельное текущее состояние
class EventService:
    async def record_event(self, data):
        # 1. Записать событие в append-only журнал
        event = self._build_event(data)
        await self._event_repo.append(event)
        # 2. Обновить текущее состояние (в той же транзакции)
        await self._state_repo.update(event)
        # 3. Поставить в outbox для downstream consumer'ов
        await self._outbox_repo.enqueue(event)
        return event
```

**Плюсы:**
- **Простота** — текущее состояние читается из проекции за O(1), не требует 
  replay при каждом чтении
- **Детерминированный replay** — события можно воспроизвести для восстановления 
  или проверки, но это не единственный путь получения состояния
- **Аудит** — append-only журнал обеспечивает полный audit trail
- **Интеграция** — события публикуются через Event Backbone для всех 
  downstream Streams
- **Гибкость** — разные Consumer'ы могут строить свои проекции из одних и тех же 
  событий

**Минусы:**
- Нельзя восстановить агрегат **только** из событий без projection'ов
- Часть состояния «зашита» в проекциях — при сбое projection'а требуется replay
- Дублирование: событие + текущее состояние могут рассинхронизироваться 
  (предотвращается транзакционной записью)

### 3. Conventional CRUD без журнала (не выбрано)

Только текущее состояние, без событийного журнала.

**Плюсы:**
- Максимальная простота
- Минимум инфраструктуры

**Минусы:**
- **Нет аудита** — невозможно ответить на вопрос «кто и когда изменил состояние»
- **Нет replay** — нельзя восстановить состояние из истории
- **Нет интеграции** — каждый downstream Stream должен сам тянуть данные
- Противоречит требованиям Epic 3 (Accounting Compliance & Reporting)

---

## Решение

**Выбрана модель: Append-only Event Log + отдельное текущее состояние.**

Ключевые принципы:

1. **События — append-only.** Никаких UPDATE/DELETE. Отмена — только через 
   компенсирующие события.
2. **Текущее состояние хранится отдельно** — в проекциях, таблицах, 
   материализованных вьюхах. Не выводится исключительно из событий при каждом 
   чтении.
3. **События используются** для:
   - Аудита (полная и неизменная история)
   - Интеграции между Streams (Event Backbone)
   - Replay (восстановление projection'ов)
   - Gap detection и recovery
4. **События НЕ являются единственным источником истины** для Business State. 
   Business State — это projection, который может быть перестроен из событий, 
   но не обязан быть построен всегда из них.

## Последствия

### Positive

✅ **Простой домен** — нет сложности Event Sourcing (snapshot management, 
   event versioning conflicts, aggregate migration)

✅ **Детерминированный replay** — одинаковые события → одинаковое состояние 
   для любого Consumer'а

✅ **Хороший audit trail** — каждое изменение зафиксировано в неизменяемом журнале

✅ **Гибкая интеграция** — downstream Streams получают события через Event Backbone

✅ **Производительность** — текущее состояние читается за O(1) из проекции

### Negative

❌ **Нельзя восстановить агрегаты только из событий** — часть состояния 
   остаётся в проекциях. Для полного восстановления нужен replay.

❌ **Часть состояния остаётся в проекциях/таблицах** — требуется синхронность 
   между записью события и обновлением проекции (решается транзакционным 
   подходом — см. Transactional Outbox).

❌ **Дублирование данных** — событие + текущее состояние могут незначительно 
   расходиться по схеме хранения (но всегда консистентны на уровне бизнес-логики)

## Влияние на другие Streams

| Stream | Влияние |
|:-------|:--------|
| **Stream 4 — Compliance State** | Восстанавливает состояние из событий через replay. Не полагается на snapshot. |
| **Stream 5 — Eligibility Engine** | Работает с текущим состоянием (cache-based). События — триггер для пересчёта. |
| **Stream 7 — Simulation** | Использует replay с модифицированными событиями («что если»). Отдельная сессия, не влияет на live state. |
| **Stream 8 — Timeline** | Строит временную шкалу из событий. Чистый projection. |
| **Stream 11 — Explainability** | Использует события для построения ReasoningGraph. Read-only доступ к журналу. |

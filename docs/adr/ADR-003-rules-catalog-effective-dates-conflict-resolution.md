# ADR-003: Rules Catalog с effective_from/effective_to, стратегия разрешения конфликтов Default Rules vs Organization Overrides

**Статус:** Draft  
**Дата:** 2026-07-23  
**Контекст:** Epic 3 — Accounting Compliance & Reporting  
**Автор:** Architect (RealtorOS)

---

## Контекст

Налоговое законодательство меняется каждый год. Разные организации могут иметь разные режимы, льготы, сроки. Правила должны обновляться без перезапуска backend. Организации могут переопределять дефолтные правила (региональные особенности, собственные сроки).

## Решение

### 1. Двухуровневое хранение

```
Default Rules (YAML/JSON в Git)
    │
    ├── Базовые правила
    ├── Законодательные новеллы
    └── Региональные особенности
    │
    ▼
Organization Override (Database)
    │
    ├── Свои сроки
    ├── Свои ставки
    ├── Дополнительные требования
    └── source: default | manual | import | law
    │
    ▼
Runtime View = Merge(Default, Override) filtered by effective_from/effective_to
```

### 2. effective_from / effective_to

Все правила имеют временные диапазоны вместо версий по годам.

```yaml
# ❌ Старый подход
# version: "УСН 2026"

# ✅ Новый подход
requirements:
  - requirement_code: req_revenue_posted
    effective_from: "2026-01-01"
    effective_to: null    # бессрочно
```

Движок автоматически выбирает правила, где `effective_from <= today < effective_to`.

### 3. Стратегия разрешения конфликтов

При слиянии Default + Override применяются следующие правила:

| Уровень | Приоритет | Пример |
|:--------|:---------:|:-------|
| Organization Override (manual) | 1 (высший) | Бухгалтер вручную изменил срок сдачи |
| Organization Override (import) | 2 | Импортировано из внешней системы |
| Organization Override (law) | 3 | Региональный закон изменяет срок |
| Default Rules | 4 (низший) | Базовый срок по НК РФ |

**Правила слияния:**

1. Всегда побеждает Override с наивысшим приоритетом (наименьший номер)
2. Если Override не задан — применяется Default
3. Если multiple Override для одного правила — побеждает последний по времени
4. invalid_from / invalid_to: если дата не входит в диапазон — правило не применяется
5. Нет каскадного наследования override (только прямое переопределение)

### 4. source — происхождение переопределения

Поле `source` в `organization_rules_overrides`:

| source | Кто создал | Когда применяется |
|:-------|:-----------|:------------------|
| `default` | Система (из Default Rules) | Исходное правило |
| `manual` | Бухгалтер через UI | Ручная настройка |
| `import` | Внешняя система | Импорт из 1С / Эльбы |
| `law` | Региональная надстройка | Законодательная новелла |

## Обоснование

| Вариант | Минусы |
|:--------|:-------|
| **Версии по годам** | Ручное переключение, `if year == 2027`, дублирование конфигов |
| **Только Deploy** | Нельзя быстро изменить правило, нельзя переопределить для конкретной организации |
| **effective_from/effective_to + Override** | Гибкость, автоматический выбор, без `if year`, без перезапуска |

## Последствия

**Positive:**
- Автоматический выбор правил по дате — без `if year == 2027`
- Организации могут переопределять правила без влияния на других
- source даёт аудит: откуда взялось правило
- Default Rules в Git — code review изменений
- Override в Database — быстрые изменения через UI

**Negative:**
- Сложность Runtime View: нужно мержить Default + Override на каждый запрос
- Риск конфликта Override с новым Default после деплоя
- effective_to может быть пропущен — правило остаётся навсегда (mitigation: аудит правил с истёкшим effective_to)
